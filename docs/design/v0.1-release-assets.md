## 0. 현재 상태 (왜 이게 v0.1을 막는가)

| 항목 | 현재 | 영향 |
|---|---|---|
| Android 런처 아이콘 | `AndroidManifest.xml`이 `@mipmap/ic_launcher` 참조하는데 `android/app/src/main/res/`에 `mipmap-*` 디렉터리가 **아예 없음** | **`flutter build apk`/`appbundle`가 리소스 없음으로 실패** — 빌드 자체가 안 됨 |
| iOS 앱 아이콘 | `ios/Runner/`에 `Assets.xcassets`(AppIcon) **없음** | iOS 아카이브 시 아이콘 누락 경고/거부. (v0.1이 Android 우선이면 후순위지만 곧 필요) |
| 스토어 등재 자산 | 앱 이름만 확정(`android:label`/`CFBundleDisplayName` = "곁에", 번들ID `com.gyeote.app`) | 짧은/긴 설명, 스크린샷, 개인정보처리방침 URL 없이는 스토어 제출 불가 |
| 개인정보처리방침 | 없음 | 위치를 상시 수집·공유하는 앱이라 **스토어 심사에서 반드시 걸림** (Google Play Data safety + 한국 위치정보법) |

브랜드 시드 색: 앱 테마 `colorSchemeSeed: Colors.pinkAccent` = **`#FF4081`** (Material 3).

### 1-1. 확정 결론

- **v0.1은 "완벽한 아이콘"이 아니라 "아이콘이 아예 없음"이 문제다.** 임시안이라도
  넣으면 출시된다. 아래 임시안을 v0.1 기준으로 확정하고, 정식 일러스트는
  v0.2에서 교체한다(아이콘 교체는 스토어 재심사 사유 아님).
- **Adaptive icon(Android 8.0+ / API 26+) 방식을 쓴다.** 단색 배경 + 전경
  심볼 분리라 임시안 제작이 쉽고, 런처별 마스크(원형/스퀴클/둥근사각)에
  자동 대응된다. 레거시(API 25 이하)용 정사각 PNG도 같은 소스에서 함께
  생성한다.
- **제작·생성은 `flutter_launcher_icons` 패키지로 일괄 처리**한다(아래 1-4).
  Diana는 소스 PNG 2장만 준비하면 Android 전 밀도 + adaptive XML + iOS
  전 사이즈가 자동 생성된다.

### 1-2. 아이콘 디자인 스펙 (v0.1 임시안)

| 요소 | 값 |
|---|---|
| 배경 | 단색 `#FF4081` (브랜드 시드와 동일). v0.2에서 `#FF4081 → #FF6F9C` 세로 그라데이션 검토, v0.1은 단색 |
| 전경 심볼 | 흰색(`#FFFFFF`), 불투명 |
| 심볼 1안 (권장) | **두 개의 물방울형 위치 핀이 서로 기대어 겹친 형태.** 겹치는 영역은 배경 핑크가 비쳐 하트 실루엣을 암시. "곁에(옆에 있다) + 위치"를 한 번에 나타냄 |
| 심볼 2안 (1안 제작이 지연되면 폴백) | 흰색 한글 **"곁"** 한 글자. 둥근 산세리프(Pretendard SemiBold / 여기어때 잘난체 계열 등 라운드 웨이트), 시각 중심 정렬 |
| 심볼이 차지하는 비율 | adaptive 전경 캔버스(108dp 상당)의 **가운데 66dp 세이프존 안**에 완전히 들어오도록. 대략 캔버스 폭의 60% 이하 |
| 여백 | 심볼 외곽에서 캔버스 가장자리까지 최소 18% 패딩(런처가 가장자리를 잘라냄) |

트레이드오프 메모: 2안(한글 한 글자)은 제작이 가장 빠르고 한국 시장에서
식별성도 나쁘지 않지만, 글로벌 확장 시 재작업 가능성이 있다. 1안이 브랜드
자산으로 오래 간다. **v0.1 출시 일정이 촉박하면 2안으로 내보내고 v0.2에서
1안으로 교체**하는 걸 허용한다.

### 1-3. 소스 에셋 규격 (Din이 이 규격대로 제작·전달 완료)

`app/assets/icon/` (커밋됨):

| 파일 | 사양 | 용도 |
|---|---|---|
| `app_icon.png` | 1024×1024, **불투명**, 핑크 배경 풀블리드 + 흰 심볼(가운데 60%) | iOS 아이콘 + Android 레거시 정사각 + 스토어 아이콘 소스 |
| `app_icon_foreground.png` | 1024×1024, **투명 배경**, 흰 심볼만. 심볼은 가운데 약 640px(≈66%) 세이프존 안 | Android adaptive 전경 |
| `app_icon_monochrome.png` | (선택) 1024×1024, 투명 배경, 심볼 실루엣 단색 흰색 | Android 13+ 테마 아이콘. 시간 없으면 생략 |

- iOS는 알파(투명) 허용 안 함 → `app_icon.png`는 배경을 반드시 채운다.
- 512×512 스토어 아이콘은 `app_icon.png`를 축소해서 별도 저장(1-5 참조).

### 1-4. 생성 파이프라인 (`flutter_launcher_icons`)

**Diana가 `app/pubspec.yaml`에 이미 배선해 뒀다**(dev_dep `^0.14.1` + 설정
블록). 현재 설정:

```yaml
flutter_launcher_icons:
  image_path: "assets/icon/app_icon.png"
  android: "ic_launcher"
  min_sdk_android: 23
  adaptive_icon_background: "assets/icon/app_icon_background.png"
  adaptive_icon_foreground: "assets/icon/app_icon_foreground.png"
  ios: true
  remove_alpha_ios: true
```

전달한 원본 파일명이 이 설정과 그대로 맞는다. `adaptive_icon_background`는
색 문자열(`"#FF4081"`)로 줄여도 되지만 PNG 경로(`app_icon_background.png`,
단색 핑크)도 동일 결과라 그대로 둔다. Android 13 테마 아이콘을 쓰려면
`adaptive_icon_monochrome: "assets/icon/app_icon_monochrome.png"` 한 줄
추가(원본은 이미 전달함).

실행: `cd app && dart run flutter_launcher_icons`

생성 결과(커밋 대상):
- `android/app/src/main/res/mipmap-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}/ic_launcher.png`
  (48/72/96/144/192 px)
- `android/app/src/main/res/mipmap-anydpi-v26/ic_launcher.xml` (+ `ic_launcher_round.xml`)
- `android/app/src/main/res/values/colors.xml` (`ic_launcher_background` = `#FF4081`)
- `android/app/src/main/res/drawable*/` 전경 리소스
- `ios/Runner/Assets.xcassets/AppIcon.appiconset/` 전 사이즈 + `Contents.json`

매니페스트의 `android:icon="@mipmap/ic_launcher"`는 그대로 두면 된다(경로 일치).

### 1-5. 절대 최소 폴백 (임시 아트도 지연될 때)

빌드만 통과시켜야 하면: `mipmap-{mdpi~xxxhdpi}` 디렉터리를 만들고 각기
**단색 핑크(`#FF4081`) 정사각 `ic_launcher.png`** 한 장씩만 넣어도
`flutter build`는 성공한다. 심볼 없는 핑크 사각형이라도 출시는 되고,
다음 커밋에서 심볼을 얹는다. — 단 이건 정말 마지막 수단이고, 1-4 파이프라인이
반나절이면 끝나므로 되도록 임시안(1-2)까지는 하고 내보낸다.

### 1-6. 스플래시 화면 (참고, 빌드 차단 아님)

현재 `splash_screen.dart`는 `CircularProgressIndicator`만, Android
`launch_background.xml`은 흰 배경만. v0.1 필수는 아니지만 아이콘 소스가
생기면 같은 심볼을 흰 배경 중앙에 얹는 정도는 저비용이다(Diana 재량,
v0.1 여유 있으면).

## 2. 스토어 등재 자산 — [필수]

대상: **Google Play 우선**(내부 테스트 → 비공개 테스트 → 프로덕션). App Store는
아이콘·심사 리드타임 있어 병행하되 Play를 먼저 낸다.

### 2-1. 앱 이름 / 기본 정보

| 항목 | 값 |
|---|---|
| 앱 이름 | 곁에 |
| 패키지/번들 ID | `com.gyeote.app` (Android `applicationId`, iOS `CFBundleIdentifier` 모두 확정됨) |
| 카테고리 | 소셜 (대안: 라이프스타일) |

> **2-2 / 2-3 스토어 설명: 가인님 승인 (2026-09-03).** v0.1에 없는 기능(사진첩·

### 2-2. 짧은 설명 (Google Play, 공백 포함 80자 이내)

> **멀리 있어도 서로의 위치를 안전하게. 커플·가족·친구를 위한 위치 공유 앱.**

(38자. **v0.1에 없는 사진첩·버킷리스트는 넣지 않는다** — 심사에서
"설명에 있는 기능이 앱에 없음"으로 반려될 수 있음.)

### 2-3. 긴 설명 (Google Play, 4000자 이내)

```
곁에는 멀리 떨어져 지내는 커플·가족·친구가 서로의 위치를 안심하고 나눌 수 있는 앱이에요.

■ 그룹별로 공개 범위를 따로
관계마다 보여주고 싶은 만큼만 정할 수 있어요.
- 정밀: 정확한 위치를 실시간으로 공유
- 대략: 실제 위치에서 반경 약 100m로 뭉뚱그려 공유
- 끄기: 이 그룹에는 위치를 전혀 보여주지 않음

■ 잠깐 꺼두기
"30분만 일시중지"처럼 원하는 시간만 잠깐 숨길 수 있어요. 시간이 지나면 설정한 대로 자동으로 다시 공유돼요.

■ 프라이버시가 먼저예요
- 모든 그룹에서 공유를 꺼두면 서버에 위치가 저장되지 않아요.
- 이동 기록은 최대 14일까지만 보관하고 자동으로 지워요.
- "대략" 모드의 좌표 하향 처리는 서버에서 강제로 이뤄져, 정확한 위치가 상대에게 전달되지 않아요.

■ 관계 그룹과 초대
커플·가족·친구 그룹을 만들고 초대 코드로 상대를 초대하세요. 초대 코드는 7일 후 만료돼요.

곁에는 위치 공유 기능을 위해 기기의 위치 정보를 사용해요. 앱을 사용하는 동안 위치를 수집하며, 공유를 켜 둔 그룹의 구성원에게만 보여요.

앞으로 사진과 버킷리스트를 함께 나누는 기능이 추가될 예정이에요.
```

- 마지막 "앞으로 …" 문장은 심사관에 따라 "미출시 기능 언급"으로 볼 수 있음.
  반려되면 이 한 줄만 빼고 재제출. (그래서 맨 끝에 배치)
- 백그라운드 위치를 v0.1에서 실제로 요청하지 않으므로 "always/배경 위치"
  표현은 쓰지 않았다. `ACCESS_BACKGROUND_LOCATION` 매니페스트 선언은 이후
  제거됐다(2-6-1, `7349086`) — Play가 선언만으로도 배경 위치 정책 심사를
  요구할 수 있었기 때문.

### 2-4. 스크린샷 구성안

Google Play 요구: 폰 스크린샷 **최소 2장, 최대 8장**, 16:9 또는 9:16,
각 변 320~3840px. **9:16 세로 1080×1920 권장.**

v0.1 제출용 6장(순서 = 스토어 노출 순서):

| # | 화면 | 캡션(상단 오버레이) | 촬영 메모 |
|---|---|---|---|
| 1 | 홈 | **"지금 누구에게 보이는지 한눈에"** | 공유 상태 요약 캡션이 "OO, OO에게 공유 중"으로 채워진 상태(P1-6). 더미 그룹 2개 |
| 2 | 위치 지도 | **"멀리 있어도, 지도 위에서 함께"** | 피어 마커 2~3개(정밀 파랑 + 대략 주황 섞어서), 신선도 칩 "3분 전" 표시 |
| 3 | 위치 공유 설정 | **"그룹마다 공개 범위를 따로"** | 상단 배너 + 그룹 카드 2개, 하나는 정밀 하나는 대략 세그먼트 선택 상태 |
| 4 | 일시중지 UI | **"잠깐 숨기고 싶을 땐 일시중지"** | "30분만 일시중지" 눌린 뒤 "오후 3:32까지 일시중지됨" 캡션(P1-2) |
| 5 | 그룹 상세 / 초대 코드 | **"초대 코드로 간단하게"** | 초대 코드 생성된 다이얼로그 or 코드 표시 상태 |
| 6 | 권한 프라이밍 | **"위치 권한이 왜 필요한지 먼저 설명해요"** | 권한 요청 전 프라이밍 화면. 프라이버시 신뢰 강조 |

- 최소 제출은 1·2·3번 3장. 6장 다 준비되면 전환율에 유리.
- 캡션 오버레이 템플릿: 1080×1920 캔버스, 상단 0~18% 영역에 캡션(24~28pt,

## 3. 개인정보처리방침 초안 — [v0.1 필수]

아래는 **초안**이다. 법률 검토 전이며, 사업자 정보·연락처·호스팅 URL은
placeholder(`[[ ]]`)다. 위치를 상시 수집·공유하는 앱이라 심사에서 가장
많이 걸리는 부분이므로 v0.1 필수 산출물로 잡는다.

근거 데이터(코드/마이그레이션에서 직접 확인, 2026-09-03):

| 데이터 | 저장 위치 | 구성 | 보존 |
|---|---|---|---|
| 이메일, 비밀번호 | Supabase Auth (`auth.users`) | 비밀번호는 해시 저장 | 계정 삭제 시까지 |

- 광고 SDK, 분석(analytics) SDK, 크래시 리포팅 **없음**(코드 전수 확인).
- 푸시 알림 토큰 수집 **없음**(v0.1).
- 처리 위탁: **Supabase**(인증·DB·실시간 통신 호스팅), **Google Maps SDK**
  (지도 표시 — 지도 렌더링을 위해 기기 위치가 Google에 전달될 수 있음).

**위치정보 수집 범위 — 포그라운드 한정, 문구는 코드가 보장하는 것만
(Rena 2차 검증, 2026-09-05)**: Rena가 `location_collector_service.dart`를
검증한 결과 백그라운드/포그라운드 서비스 코드가 전혀 없는 **순수 포그라운드
`Timer.periodic`**(5분 하트비트)이고, Diana가 `7349086`으로
`ACCESS_BACKGROUND_LOCATION`(Android)과 iOS `NSLocationAlwaysAndWhenInUseUsageDescription`
문구까지 제거했다. 다만 최초 방침 문구("백그라운드로 전환되면 위치 수집이
**즉시 중단**됩니다")는 Rena의 2차 검증에서 **코드가 뒷받침하지 않는 문장**
으로 지적됐다: `location_collector_service`에 `AppLifecycleState` 처리가
없어서, 그 "중단"은 앱이 보장하는 게 아니라 **OS가 백그라운드 프로세스를
정지시키는 데 의존**한다. whileInUse 권한 상태로 앱이 백그라운드로 간 뒤
OS 유예 구간(수 초~수 분) 동안 5분 하트비트 타이머나 진행 중이던 position
콜백이 발화하면 실제로 위치가 전송될 수 있다.

→ **가인님 결정(2026-09-05): 문구를 완화한다.** "포그라운드 전용으로
동작하며, 백그라운드에서는 OS가 앱 실행을 제한합니다" 수준으로 —
**코드가 실제로 보장하는 것만 적는다.** 이유 둘: (1) 법적으로 게시되는
문서에 지킬 수 없는 약속을 적으면 안 되고, (2) 릴리즈 직전에 이미 검증
끝난 수집 로직을 문구 때문에 건드리는 위험을 지지 않는다. 라이프사이클
연동으로 "즉시 중단"을 코드가 실제로 보장하게 만드는 건 **v0.2 티켓으로
이연**(아래 §7).

(실제 반영: `docs/legal/privacy.html`의 강조 박스 + 제6조.)

쓴다:

## 7. v0.2 이연 — 위치 수집의 라이프사이클 연동 (Rena 지적, 가인님 결정 2026-09-05)

**티켓**: `location_collector_service`가 `AppLifecycleState`를 구독하지 않아,
앱이 백그라운드로 전환돼도 코드 차원에서 수집을 멈추지 않는다. 현재는
whileInUse 권한 + OS의 백그라운드 프로세스 정지에 기대는 상태라, OS 유예
구간 동안 5분 하트비트 타이머나 진행 중이던 위치 콜백이 발화하면 위치가
전송될 수 있다(방침 문구를 완화한 이유, §3-2 참고).

**v0.2에서 할 일**: `WidgetsBindingObserver`로 `AppLifecycleState.paused`/
`resumed`를 구독해 백그라운드 진입 시 `_heartbeatTimer`를 명시적으로
취소하고 포그라운드 복귀 시 재시작한다. 이게 들어가면 방침 문구를
"백그라운드로 전환되면 위치 수집이 중단됩니다"로 다시 강화할 수 있다 —
**문구 강화는 이 코드 변경이 실제로 배포된 뒤에만** 진행한다(순서를
바꾸지 않는다).

**v0.1에서 안 하는 이유(가인님)**: 릴리즈 직전에 이미 검증 끝난 수집 로직을
문구 정합성 때문에 건드리는 위험을 지지 않는다. 법적 문서는 코드가 지금
보장하는 것만 적는 쪽이 맞다.
